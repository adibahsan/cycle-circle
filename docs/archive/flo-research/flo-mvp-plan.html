Technology Stack
Chosen for speed of development, zero-config deploys, and the ability to graduate to ML without rewriting the backend. All selections match the research doc recommendations.
Frontend
Next.js 14 + TypeScript
SSR, API routes, routing, and React in one repo. App Router for layouts.
Styling
Tailwind CSS
Fast iteration. Consistent design tokens. No CSS context-switching.
State Management
Zustand + SWR
Lightweight global state. SWR for server state + cache invalidation after logs.
Backend + Auth + DB
Supabase
PostgreSQL + Auth + real-time subscriptions + Row Level Security out of the box.
Prediction Engine (MVP)
Pure TypeScript function
No ML needed yet. Simple average-based algorithm runs in the API route. Swap for scikit-learn in Phase 3.
Calendar / Charts
date-fns + Recharts
date-fns for all date math. Recharts for cycle length trend charts in Phase 2.
Hosting
Vercel
Zero-config Next.js deploys. Preview URLs on every PR. Free for MVP scale.
Payments (Phase 2)
Stripe
Subscriptions, FSA/HSA card support, webhooks for entitlement sync.

MVP Prediction Algorithm
No ML needed for launch. This simple average-based algorithm reduces prediction error enough to be genuinely useful. Swap for ARIMA or neural nets in Phase 3 once you have data.
// MVP Cycle Prediction — Pure TypeScript, runs in Next.js API route // Step 1: Compute average cycle length from logged period history const avgCycleLength = periodLogs.length >= 3 ? average(periodLogs.map(p => daysBetween(p.start, nextLog.start))) : user.avg_cycle_length; // fall back to onboarding value // Step 2: Predict next period const nextPeriodStart = addDays(lastPeriodStart, avgCycleLength); const nextPeriodEnd = addDays(nextPeriodStart, user.avg_period_length); // Step 3: Ovulation = next period start minus 14 days (luteal phase constant) const ovulationDate = subDays(nextPeriodStart, 14); const fertileWindowStart = subDays(ovulationDate, 5); // sperm survive 5 days const fertileWindowEnd = addDays(ovulationDate, 1); // egg survives ~24 hrs // Step 4: Assign day colour for calendar rendering const getDayType = (date) => { if (isPeriodDay(date)) return 'period'; // red/pink if (isOvulationDay(date)) return 'ovulation'; // teal dashed ring if (isFertileDay(date)) return 'fertile'; // teal fill return 'low'; // dark/neutral }; // Phase 3 upgrade path: replace avgCycleLength calc with ARIMA or LSTM model // trained on user's full history via Python/FastAPI sidecar service

Key Risks & Mitigations
Ranked by likelihood × impact for the 2-week window.
High
Scope creep on onboarding
Onboarding easily expands from 3 screens to 10+. Each extra question delays dashboard development and prediction testing.
→ Mitigate: Hard cap at 3 screens for MVP. Add lifestyle questions and social proof in Phase 2 onboarding update. Design the questions to be additive — they can slide in later without reworking the data model.
High
Calendar rendering complexity
Building a monthly calendar grid that handles DST, different month lengths, and correct colour-coding is deceptively complex. Spans across predictions + period_logs tables.
→ Mitigate: Use date-fns for all date arithmetic (not raw Date objects). Build a single getDayMeta(date, predictions, periodLogs) util function on Day 4 and test it in isolation before connecting to the UI.
Medium
Cold-start prediction accuracy
First-time users with no period history get predictions based purely on the cycle length they enter during onboarding. This will be inaccurate for users with irregular cycles.
→ Mitigate: Show "This is an estimate — accuracy improves after 3 logged cycles" on the dashboard until 3 cycles are logged. Use the entered cycle length as Cycle 1 baseline data point.
Medium
Supabase RLS misconfiguration
Row Level Security is critical — if misconfigured, users could read other users' period data. This is a legal and reputational risk, not just a bug.
→ Mitigate: Write RLS policies on Day 2 and test them explicitly with two test accounts. Add an RLS audit checklist to the Day 10 definition of done. Never disable RLS "just for now."
Low
Prediction engine not triggered on retroactive edits
If a user edits a past period date, the predictions table must recalculate. Easy to forget this edge case when building the period log edit flow.
→ Mitigate: Centralise prediction triggering in a single recalculatePredictions(userId) server function called by all period log mutations (create, update, delete). Never call the algorithm from the frontend.
