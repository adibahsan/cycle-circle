# Vesta v1.4.0

Building on **v1.3.0** — cron management, email-trial UX, cache overhaul, contact uniqueness, subscription tier fixes, SMS broadcasts, API docs, and significant performance improvements.

**Deployed:** Vercel (web + admin) + Supabase migration `20260629120000_v1_4_consolidated`

---

## Highlights

### Admin app — system management

- **Cron enable/disable toggle** — admin `/system` page now shows each scheduled cron job with a live enable/disable toggle. State is persisted via a new `CronSetting` DB model; the web cron routes read the setting and skip execution when disabled.
- **Bilingual + bulk SMS broadcast UI** — new SMS broadcast management page with bilingual (EN/BN) message entry, bulk recipient list input, and per-broadcast delivery status. Includes a daily broadcast cron with delivery-report correlation (matches sent messages to BDApps delivery receipts).
- **Self-hosted Swagger UI at `/api-docs`** — fresh OpenAPI 3.1 spec auto-served at the `/api-docs` route; no external hosting required.

### Web app — email trial & contact UX

- **Live email-trial countdown pill** — users on a free email-only account see a real-time countdown showing how many days remain on their trial before the account lapses. The pill appears in the nav and dashboard.
- **OTP add-number to keep access** — when the trial countdown expires, users are prompted to add a phone number and verify it via OTP (BDApps or DEV_MODE bypass). Adding a verified number upgrades the account to Pro and removes the trial block.
- **Contact uniqueness checks + warnings** — submitting a phone or email that is already associated with another account surfaces a clear, bilingual warning before saving. Duplicate contact submission is blocked with a typed `{ok, code}` result from the contact-save service.
- **Email normalization** — email addresses are normalised (lowercased, trimmed) consistently across all save paths before DB writes and uniqueness checks.

### Shared services — subscription tiers

- **Subscription tier fixes** — phone/OTP-verified accounts are classified as **Pro**; email-only accounts are **Free** (on trial); accounts whose email trial has expired are **Lapsed** (distinct from Free). All three states are handled by a shared `getSubscriptionTier()` helper used by both apps, replacing divergent inline logic.

### Shared services — cache overhaul

- **Central cache-tags helper** — a single `cache-tags.ts` module defines all Next.js cache tags used across both apps. Both apps import from it instead of scattering string literals.
- **Revalidate on every mutation** — all server actions (create, update, delete) in both apps now call `revalidateTag()` with the appropriate tags immediately after the DB write.
- **Cross-app web revalidation endpoint** — admin can trigger on-demand revalidation of web cache tags via a dedicated internal endpoint on the web app (secured with `CRON_SECRET`), keeping web content fresh after admin CMS edits without a full redeploy.
- **Admin unique cache keys** — admin server components use user-scoped and page-scoped cache keys to avoid stale data across different admin sessions.

### Performance

- **Code splitting** — heavy client-side libraries (Recharts, Tiptap, interaction modals, xlsx, DOMPurify) are now dynamically imported (`next/dynamic`) so they are excluded from the initial JS bundle.
- **Composite `PeriodLog(profileId, startDate)` index** — replaces a full table scan in the tracking-service date-range queries; improves calendar and insights load time for users with long history.
- **Parallelized service reads** — dashboard and insights server components now `Promise.all()` independent service calls instead of awaiting them sequentially.
- **`optimizePackageImports`** — `next.config.ts` now includes `optimizePackageImports` for Lucide and Recharts to reduce server-side import overhead.
- **Default nav prefetch** — `<Link prefetch>` enabled on primary navigation links; reduces perceived latency on route transitions.
- **Stop refetching auth/completion on navigation** — auth state and profile-completion status are no longer re-fetched on every client navigation; they are hydrated once on load and updated only on explicit user actions.

### DevOps — cron & seeding

- **Cron GET + POST handlers** — all three cron routes (`daily-reminders`, `caas-check`, `sms-daily-broadcast`) now export both `GET` and `POST`. Vercel Cron invokes routes via GET; the shared handler accepts either method safely (body is optional via `.catch(() => ({}))`).
- **Prod-safe seeding (`SEED_DEMO`)** — `packages/shared/prisma/seed.ts` now guards demo-user and dummy-user seeding behind `SEED_DEMO=true`. In production (or when the flag is absent) only the admin account is upserted, preventing test data from landing on staging/prod.

## Database migration

Migration `20260629120000_v1_4_consolidated` squashes the four individual
post-v1.3 migrations into one for maintainability. Schema additions (all
additive, safe for existing data):

```sql
-- otp_users_auto_pro: data backfill (OTP-verified users → Pro tier)
-- add_sms_circulation_fields: SmsBroadcast table + delivery-report columns
-- add_periodlog_profile_startdate_index: composite index PeriodLog(profileId, startDate)
-- add_cron_setting: CronSetting model (id, name, enabled, updatedAt)
```

### Upgrade steps

**Fresh DB** (new environment): run `migrate deploy` as usual — it applies
`0_init` → `v1_3_consolidated` → `v1_4_consolidated` in order.

**Already-deployed DB** that has some or all of the four individual migrations
in `_prisma_migrations` — use the resolve-reconciliation procedure:

> **Precondition:** the DB must be fully migrated through all four individual
> migrations *before* reconciling. If any were not yet applied, run
> `migrate deploy` against the previous codebase first, then come back here.
> Using `resolve --applied` tells Prisma to skip running the consolidated SQL,
> so any pending DDL would be silently skipped.

1. **Backup** (Supabase Free has no auto-backup):
   ```bash
   just db-backup-url "<DIRECT_URL>"
   ```

2. **Verify all four individual migrations are applied:**
   ```bash
   DIRECT_URL=… pnpm --filter @vesta/shared exec prisma migrate status
   ```

3. **Delete the four individual rows from `_prisma_migrations`:**
   ```sql
   DELETE FROM "_prisma_migrations"
   WHERE migration_name IN (
     '20260621120000_otp_users_auto_pro',
     '20260628131041_add_sms_circulation_fields',
     '20260628233111_add_periodlog_profile_startdate_index',
     '20260629112337_add_cron_setting'
   );
   ```

4. **Mark the consolidated migration as applied (no SQL re-run):**
   ```bash
   DIRECT_URL=… pnpm --filter @vesta/shared exec prisma migrate resolve \
     --applied 20260629120000_v1_4_consolidated
   ```

5. **Confirm clean status:**
   ```bash
   DIRECT_URL=… pnpm --filter @vesta/shared exec prisma migrate status
   # → "Database schema is up to date!"
   ```

## Upgrade notes

1. **Apply DB migration before deploying apps** (see procedure above).
2. **Admin Vercel env** — ensure all of the following are set:
   - `AUTH_COOKIE_NAME=vesta_admin_token`
   - `APP_URL` (web app URL)
   - `CRON_SECRET` (same value as web)
   - `DIRECT_URL` (port 5432 direct connection)
3. **Web Vercel env** — `SEED_DEMO` should be left unset (or `false`) on staging/prod to prevent demo data injection.
4. No JWT rotation required — existing sessions remain valid.

## Deferred / known gaps

- **Field encryption (FR-ENC)** — not built. `SymptomLog.value` remains plaintext; the SRS security gate requires encryption before any public launch. Deferred to v2.
- **Postgres RLS** — not active; data isolation is app-layer only (JWT → Prisma `userId` scoping). Deferred; go/no-go required before real public launch.
- **Real BDApps OTP / CAAS / SMS** — deferred (no production credentials). `DEV_MODE` bypass (`420420` / `840840`) stays on for staging. Real creds + webhook registration required before any public launch.
- **QStash async jobs** — not wired. Cron routes send email synchronously within the function timeout. Acceptable at current scale (<100 users); async job queue deferred to a future release.
- **CI/CD** — none yet. Manual gate (typecheck + tests + `next build`) runs before each deploy.
