# Vesta v1.5.0

Building on **v1.4.0**, Vesta moves off Vercel/Supabase onto a self-hosted Contabo VPS. The release adds TLS, host crons, backups, hardening and a Prometheus + Grafana monitoring stack.

**Deployed:** Contabo VPS (`62.171.155.231`) via Docker Compose (`ops/deploy/compose.prod.yml`). Let's Encrypt TLS covers `cycle-circle.com`, `www`, `admin` and `monitoring`. No new database migrations.

Specs: [#5 VPS production rollout](https://github.com/adibahsan/cycle-circle/issues/5), [#14 Monitoring stack](https://github.com/adibahsan/cycle-circle/issues/14).

---

## Highlights

### Production deploy stack (VPS)

- **Docker Compose production stack**: nginx, certbot, web, admin, Postgres and Redis, with multi-stage `Dockerfile.web` / `Dockerfile.admin`. Env files live on the host at `/opt/vesta/.env.*.production`. Only the `*.example` templates are in git.
- **TLS via Let's Encrypt**:
  - `cycle-circle.bootstrap.conf` serves HTTP during the ACME challenge.
  - `cycle-circle.conf` reads certificates directly from the certbot volume.
  - `apply-letsencrypt-nginx.sh` switches over, and `dump-le-metadata.sh` keeps a non-secret inventory in `ops/deploy/tls/`.
  - The interim self-signed path has been removed.
- **Host crons and backups**:
  - `install-vesta-crontab.sh` installs the app crons (daily reminders, CaaS check), cert renewal and the nightly `pg_dump` with `CRON_SECRET` injected.
  - The secret is substituted literally, so bash 5.2 can no longer corrupt secrets that contain `&`.
- **Host hardening**: sshd lockdown (key-only login), UFW and fail2ban. See `docs/ops/02-server-setup.md`.
- **Runbooks**:
  - DNS and production env (`docs/ops/07-dns-and-env-runbook.md`).
  - Merge to main (`docs/ops/06-merge-to-main-runbook.md`).
  - Deployment and routine release (`docs/ops/03-deployment.md`).

### Monitoring

- **Prometheus + Grafana** bundled into the production Compose project:
  - Grafana is served at `https://monitoring.cycle-circle.com`. Prometheus is internal-only.
  - TSDB retention is 30 days.
- **Exporters**: node, cAdvisor, nginx, Postgres and Redis. There is also a new **container-metrics exporter** that reads per-container CPU, memory and network from the Docker Engine API. cAdvisor can't break these out per container on the VPS's containerd snapshotter. Stats are collected in parallel so scrapes stay fast, and refresh failures are now logged instead of swallowed.
- **Grafana dashboards**: infra overview, host system, containers and services.
- **Local parity**: `pnpm docker:monitoring` runs the same stack against the local dev Compose.

### Webhooks

- Requests to the BDApps webhooks (`sms/receive`, `sms/report`, `subscription/notify`, `ussd/receive`) from IPs outside the allowlist now get **401 Unauthorized** instead of 403.

### Tooling

- **Verification scripts**:
  - `pnpm deploy:verify` checks the deploy artifacts.
  - `pnpm monitoring:verify` checks the monitoring files, scrape jobs and compose merges.
  - `pnpm vps:preflight` checks the VPS before deploying.
  - `pnpm ops:test` and `pnpm ops:test:docker` run the exporter and crontab tests. The `:docker` variant runs the crontab test under bash 5.2.
- **ESLint CLI**: web and admin now lint through the ESLint CLI (Next 16), using flat `eslint.config.mjs`.
- **Issue tracking** moved from `.scratch/` markdown to GitHub Issues. See `docs/agents/issue-tracker.md`.

## Known issues

- **BDApps billing is blocked on BDApps's side.**
  - HTTP subscription is disabled for `APP_140389`, so OTP subscribe returns `E1324`.
  - The CaaS endpoints return 404.
  - Real subscribe and charge flows are pending BDApps support. See `docs/ops/bdapps-api-test-report-2026-10-04.md`.
- Two monitoring containers (cAdvisor and container-metrics) run `privileged`, with the Docker socket mounted. A follow-up decision is pending.

## Upgrade notes (VPS)

Before the first `git pull` of this release on `/opt/vesta`:

1. Confirm `NGINX_CONF=cycle-circle.conf` in `ops/deploy/.env`. The self-signed config no longer exists.
2. Confirm `/opt/vesta/.env.monitoring.production` exists, since the monitoring stack starts with every prod `up`.
3. Then run the routine release: `git pull`, build, `up -d`, health check.
