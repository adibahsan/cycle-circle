# Phone login is the BDApps subscription; Pro means "REGISTERED on BDApps"

Phone login uses BDApps OTP (`/subscription/otp/request` + `/subscription/otp/verify`), and a successful verify subscribes the number to the app on BDApps — there is no way to verify a phone through BDApps without subscribing it. So we treat them as one step: logging in by phone subscribes the number, and the user is Pro while BDApps reports the number as `REGISTERED`. Email-only users are Free (with the existing 24h email trial) until they verify a phone the same way. When BDApps reports `UNREGISTERED` — via the subscription-notify webhook, the nightly `getStatus` check, or the in-app Unsubscribe button (`/subscription/send`, action `0`) — the user becomes Free and keeps their data; logging in by phone again re-subscribes them. Admin overrides always win. CaaS direct debit (`/api/billing/subscribe`) is parked: CaaS endpoints return 404 for our app, and BDApps subscription charging bills Pro instead. Decided 2026-10-17; supersedes the earlier "every phone user is Pro" shortcut and the SRS's CaaS-only Pro gate.

**Amendment 2026-10-18 — masked subscriber ids.** Our app (`APP_140389`) has number masking: after OTP verify BDApps addresses the subscriber by an opaque id (`tel:<base64>…:robi`), not `tel:8801…`, and rejects raw numbers on `getStatus` / `subscription/send` with E1951 (which also means "unregistered"). So we store the `subscriberId` from `otp/verify` (as `tel:<id>`) on the Subscription row and use it for getStatus, unsubscribe and webhook matching; the nightly check never downgrades a legacy row that only has a raw phone id. A successful verify counts as Pro even when BDApps reports a charging-pending status; the webhook or nightly check corrects it. Every BDApps call is written to the merchant log channel (ADR 0004; password redacted) so the real statuses and ids can be read from server logs.
