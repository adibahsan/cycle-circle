BDApps Pro API Flows with Local Simulator

A visual map for understanding SMS, USSD, and CAAS flows against the Dockerized BDApps simulator. This page is simulator-direct only: TAP UI plus the simulator REST API base. It does not involve apps/web, project API routes, auth, billing, subscriptions, or product UI.

Environment Map

Use this when the simulator is running from Docker. The simulator keeps REST on container port 7000, while this repo maps the host-facing REST port to 7002 to avoid macOS port conflicts.

Run paths

  • Simulator onlyjust simulator, or cd ops/simulator/bdapps then docker compose up -d
  • REST basehttp://127.0.0.1:7002 from your host terminal
  • UIhttp://localhost:10001/mchoice-tap-sdk

Direct health checks

Use these without starting apps/web. 

curl -fsS -o /dev/null -w "%{http_code}\n" http://localhost:10001/mchoice-tap-sdk
curl -i http://127.0.0.1:7002/
Purpose Local value How to read it
Simulator UI http://localhost:10001/mchoice-tap-sdk Open this in the browser to view phone screens, MO forms, CAAS balance controls, and status selectors.
Host REST base http://localhost:7002 Use this from your host browser or terminal. It maps to container port 7000.
Container REST base http://bdapps-simulator:7000 Use this from another service inside the Docker Compose network.
Optional receiver base http://host.docker.internal:<port> Use only if you run your own standalone receiver for simulator UI MO callbacks.

UI-first testing loop

Keep http://localhost:10001/mchoice-tap-sdk open as the visual console. Pick the matching SMS, USSD, or CAAS tab, send the API request directly to http://127.0.0.1:7002, then watch the simulator screen update.

  • SMS and OTP-style messagesCall /sms/send; the text appears in Customers Phone and Messages sent to Customer. For an OTP test, send the OTP as the SMS body.
  • USSDCall /ussd/send with a stable sessionId; inspect the USSD tab's simulated phone/session state.
  • CAASSet balance and forced status in the CAAS tab first; call balance or debit endpoints, then query again to confirm the account state.

For a customer-to-service-to-customer loop, first send MO from the simulator UI into a standalone receiver URL that you control, then send the service response back with /sms/send or /ussd/send. This guide does not use apps/web for that receiver.

Direct Simulator Mental Model

Keep this page scoped to the simulator. The UI is where you observe state; the REST API is how you trigger MT SMS, USSD prompts, balance queries, and debits.

->
Simulator REST API Call http://127.0.0.1:7002/sms/send, /ussd/send, and CAAS endpoints directly.
->
Optional standalone receiver Only needed when using simulator UI MO forms. It can be any test service outside apps/web.
Important boundary MT SMS, USSD MT, CAAS balance, and CAAS debit can be tested directly against the simulator. MO callbacks from the simulator UI require some HTTP receiver, but that receiver is outside this direct simulator guide.

Flow Catalog

Each card names the goal, path, payload focus, and success signal.

Outbound

SMS MT

Send an SMS or OTP-style message to the phone simulated by the BDApps UI.

  • Simulator/sms/send
  • FieldsapplicationId, password, message, destinationAddresses
  • SuccessS1000 and message visible on simulator phone.
Session

USSD MT/MO

Stateful menu-style session using sessionId and ussdOperation.

  • Simulator/ussd/send
  • FieldssessionId, ussdOperation, destinationAddress
  • SuccessS1000 and session prompt visible in UI.
CAAS

CAAS Balance

Reads simulator-held account state, balance, account type, and account status.

  • Simulator/caas/balance/query
  • FieldssubscriberId, paymentInstrumentName, currency
  • SuccesschargeableBalance with S1000.
Charge

CAAS Direct Debit

Charges the simulator account and shows success or balance-related failures.

  • Simulator/caas/direct/debit
  • FieldsexternalTrxId, amount, subscriberId
  • SuccessinternalTrxId and S1000.

Simulator UI MO Callbacks

The simulator UI can send MO SMS and USSD payloads to any HTTP URL you provide. For this direct guide, use your own standalone receiver if you need to inspect those inbound payloads. Do not route these examples through apps/web.

SMS MO to your receiver

Simulator posts a subscriber-originated SMS to your standalone test service.

  • Example URLhttp://host.docker.internal:5555/mo-receiver
  • UI locationSMS tab, Send Message To Application.
  • Visible replySend a follow-up MT response through /sms/send.

SMS report to your receiver

Delivery status report for an MT request with delivery report enabled.

  • Example URLhttp://host.docker.internal:5555/sms-report
  • UI optionTick delivery report required, then provide the report URL.
  • Join keyrequestId ties report back to the original send.

USSD MO to your receiver

Simulator posts a subscriber-originated USSD step to your standalone test service.

  • Example URLhttp://host.docker.internal:5555/ussd-receiver
  • UI locationUSSD tab customer/session form.
  • SessionsessionId persists across the conversation.

Receiver boundary

The receiver is not part of the simulator API. It is only a target URL for MO callbacks.

  • Direct MTUse simulator REST for the visible response.
  • No web appNo project API route is required for this guide.
  • Docker hostUse host.docker.internal when receiver runs on the host.

Step-by-Step Sequences

Use these when you need to know who calls whom and what to inspect afterward.

SMS MT: direct API sends to simulator phone
Open the SMS tab
Use the simulator UI as the phone screen. Keep Customers Phone and Messages sent to Customer visible.
Send request directly to simulator
POST http://127.0.0.1:7002/sms/send
Simulator validates fields
It returns S1000 or an error code, sometimes nested in destinationResponses.
Inspect result
Look at the API response and the simulator Customer Phone / Messages sent to Customer panels. To mimic an OTP screen, send a message such as Your OTP is 420420.
SMS MO and delivery report: simulator calls your receiver
Open simulator SMS MO screen
Set the URL to a standalone receiver such as http://host.docker.internal:5555/mo-receiver.
Optional report URL
Tick Delivery Report Required and paste the SMS report callback URL.
Send from simulator
The simulator sends the MO payload to your receiver and expects S1000.
Inspect receiver log
Confirm your standalone receiver saw the payload.
Send visible reply
To see a confirmation or OTP on the simulator phone, follow with an SMS MT request to /sms/send.
USSD: stateful session round trip
Open the USSD tab
Use the simulator UI to see the customer-facing USSD prompt and session state.
Start or continue a session
Use mo-init or mo-cont from simulator UI, or mt-cont with direct /ussd/send.
Preserve session id
The same sessionId must travel through each leg.
Send visible reply
Use /ussd/send to return the service prompt or confirmation to the simulator USSD screen.
End when needed
Use mt-fin when the app closes the session.
CAAS balance and direct debit
Open the CAAS tab
Use this tab as the account-state control panel before calling CAAS APIs.
Set simulator account state
Use simulator UI to set balance, account type, account status, and optional error status.
Query balance
Call simulator /caas/balance/query directly.
Debit amount
Call simulator /caas/direct/debit directly with a unique externalTrxId.
Inspect and test failure
Re-query balance after success. Lower balance or force status code to see insufficient-balance and simulator-error behavior.

Status Code Cheat Sheet

Keep the common codes visible while testing. The simulator guide and API appendix do not always phrase every code identically.

S1000

Success. The request was accepted or the callback acknowledgement succeeded.

E1312

Malformed or invalid request. Check required fields and JSON shape.

E1313

Authentication failed. Check application id and password.

E1325

Insufficient fund or invalid MSISDN wording depending on guide context. Use with care.

E1326

Insufficient balance or charging not allowed in common CAAS tests.

E1360

Internal error. Useful for generic failure-path checks.

E1361

System error. Useful for generic failure-path checks.

P1001

Partial success. Triggered by special simulator number 9900000.

Special numbers The simulator can return fixed responses for selected numbers. Useful examples: 9900000 -> P1001, 9900001 -> E1300, 9900014 -> E1313, 9900026 -> E1325, 9900061 -> E1360, 9900062 -> E1361.

What Is Actually Tested?

The same looking payload can prove very different things depending on the path you send it through.

Test level Path What it proves What it does not prove
Simulator direct http://localhost:7002/* The vendor simulator accepts the JSON shape and returns expected status codes. Any application business logic, persistence, auth, or webhook handling.
Simulator UI MO http://host.docker.internal:<port>/* The simulator can POST subscriber-originated payloads to a receiver you control. That the receiver is part of this repo or that it sends replies automatically.
CAAS UI state CAAS tab plus direct CAAS endpoints Balance, account status, success, and insufficient-balance simulator behavior. Real charging or production billing contracts.

Troubleshooting

Fast checks for the usual local simulator snags.

REST root returns 404

That can be normal. Test endpoint-specific POSTs such as /sms/send or /caas/balance/query.

Port 7000 is busy

macOS often uses port 7000. This repo maps host 7002 to container 7000.

Callback URL fails

If simulator runs in Docker and your standalone receiver runs on the host, use host.docker.internal, not localhost, in simulator callback fields.

Auth error

E1313 usually means the simulator rejected the app id or password pair. Use the sample local values unless testing failure paths.

Insufficient balance

Set enough balance in the simulator CAAS UI before direct debit, or use the failure deliberately to confirm error handling.
