    **Cycle Service (packages/api/src/services/cycle.service.ts):**

    Create a cycle service class with Prisma-backed methods:

    1. `logPeriodStart(profileId, data)`: Check for open cycle first (WHERE profileId AND endDate IS NULL). If exists, throw 409 Conflict "Active period exists -- end it before starting a new one." Otherwise, create CycleLog with startDate + flowIntensity. After creation, enqueue prediction recalculation job.

    2. `logPeriodEnd(profileId, cycleId, data)`: Find cycle by id + profileId. Validate endDate >= startDate. Update endDate. After update, enqueue prediction recalculation job (cycle length is now computable).

    3. `updateCycle(profileId, cycleId, updates)`: Find by id + profileId. Apply partial updates (startDate, endDate, flowIntensity). Validate date ordering if both dates present. After update, enqueue prediction recalculation job.

    4. `getCycles(profileId, options?)`: Query CycleLog WHERE profileId, ordered by startDate DESC. Support optional date range filter.

    5. `getCycleLengths(profileId)`: Get all completed cycles (endDate IS NOT NULL) ordered by startDate ASC. For each pair of consecutive cycles, compute length = nextCycle.startDate - currentCycle.startDate in days using date-fns differenceInDays. Return number[].

    6. `deleteCycle(profileId, cycleId)`: Find by id + profileId, delete.

    Store as DATE (not TIMESTAMP) per research anti-pattern guidance. Use date-fns for all date arithmetic.

    - PUT `/:cycleId` -- updateCycle (updateCycleSchema validation)
    - GET `/` -- getCycles (optional query params: startAfter, startBefore)
    - DELETE `/:cycleId` -- deleteCycle

    **Prediction Service (packages/api/src/services/prediction.service.ts):**

    Replace the Phase 1 Tier-1-only prediction service with the full factory-backed version:

    1. `generatePrediction(profileId)`:
       - Call cycleService.getCycleLengths(profileId) to get completed cycle lengths
       - If zero cycles, use the profile's onboarding cycle length estimate for Tier 1
       - Call getPredictionEngine(cycleLengths.length) to get the right tier
       - Get the most recent cycle's startDate and the profile's average period length
       - Call engine.predict(cycleLengths, lastPeriodStart, periodLength)
       - Save the result to the Prediction table via Prisma (upsert: one active prediction per profile)
       - Return PredictionResult with tier used and data points count

    2. `getLatestPrediction(profileId)`:
       - Query Prediction table WHERE profileId, ORDER BY createdAt DESC, LIMIT 1
       - If no prediction exists, call generatePrediction
       - Return CyclePrediction

    3. `predictMultipleCycles(profileId, count=3)`:
       - Generate predictions for the next `count` cycles (for calendar CALR-02)
       - For each subsequent cycle, use the previous prediction's nextPeriodStart as the new lastPeriodStart
       - Return array of CyclePrediction

    **Prediction Routes (packages/api/src/routes/prediction.routes.ts):**

    Mount on `/profiles/:profileId/predictions`:
    - GET `/` -- getLatestPrediction (returns single prediction with tier + confidence)
    - GET `/multi?count=3` -- predictMultipleCycles (returns array for calendar)
    - POST `/recalculate` -- force prediction recalculation (used by admin or debug)

    All routes: verifyJWT -> checkProfileOwnership -> controller.

    For CYCL-05 (immediate recalculation): When Tier 1 is selected (<6 cycles), run prediction synchronously (< 10ms). When Tier 2/3 is selected, enqueue via BullMQ. The cycle service should check the tier threshold and decide sync vs async.
